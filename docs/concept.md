# PHP Stubs Library Concept Document

## 1. Context

**Problem Statement**
PHP static analysis engines must distinguish built-in entities from user-defined code at every call site, class reference, and constant access. Beyond existence checks, analyzers need type metadata (parameter types, return types, constant values) and dataflow summaries (which parameters' data flows to the return value). This information is intrinsic to PHP built-in functions and independent of any particular analysis technique.

**System Role**
This library provides a read-only, immutable registry of PHP built-in entity signatures and dataflow rules, loaded from YAML files at startup.

**Data Flow**
- **Inputs:** YAML files organized in category subdirectories under `stubs/`
- **Outputs:** Existence checks, type metadata, constant values, dataflow rules
- **Connections:** YAML files (bundled resources) -> [PhpStubs registry] -> [Consumer modules]

**Scope Boundaries**
- **Owned:** YAML loading, tag-based parsing, eager loading to immutable maps, existence checks, type metadata, constant values, dataflow summaries (`flowsToReturn`)
- **Not Owned:** Taint analysis (source/sink/sanitizer classification), security rules, analysis algorithms, framework-specific value types

## 2. Concepts

**Conceptual Diagram**
```
Data Extraction (offline, one-time):
    phpstorm-stubs (.php)  ->  extraction  ->  signatures (tag, name, params, return)
    psalm stubs (.phpstub) ->  extraction  ->  dataflow   (flowsToReturn)
                                    |
                             stubs/**/*.yaml (by category subdirectory)

Runtime Loading:
    stubs/
    ├── core.yaml                     <- core constructs, Exception hierarchy
    ├── standard/standard_1..8.yaml   <- standard library (split across 8 files)
    ├── database/ network/ crypto/    <- extension categories (10 subdirectories)
    ├── text/ file/ xml/ image/
    └── system/ misc/
            |  index.txt (auto-generated by Gradle processResources)
            v
    StubRegistry (immutable, 6 typed maps):
      functions, classes, methods, constants, classConstants, properties
```

**Core Concepts**

- **Name:** Tag-Based Entity Classification
- **Definition:** Each YAML entry carries a `tag` field identifying its entity type: `function`, `method`, `class`, `constant`, `class_constant`, or `property`. The tag determines which fields are required and how the entry is parsed. File names serve only as organizational grouping (by PHP extension), not as semantic classifiers.
- **Scope:** All PHP built-in entities across all extensions.
- **Relationships:** A single YAML file contains entries with mixed tags. The parser dispatches on the `tag` field, not the filename.

- **Name:** Unified YAML Format
- **Definition:** All stub data stored as YAML files organized in 10 category subdirectories (`standard/`, `database/`, `network/`, `text/`, `crypto/`, `file/`, `xml/`, `image/`, `system/`, `misc/`) plus a top-level `core.yaml`. Each file contains a flat list of self-describing entries. Human-readable, directly editable, git-diffable.
- **Scope:** Covers functions, methods, classes, constants, class constants, and properties across all PHP extensions.
- **Relationships:** Files loaded eagerly at startup into immutable maps keyed by entity name.

- **Name:** Stub Record Hierarchy
- **Definition:** A stub record is one member of a closed hierarchy with six subtypes, one per entity kind: functions, methods, classes, constants, class constants, and properties. Each subtype carries only the fields relevant to its entity kind. All subtypes share a common name and extension identity.
- **Scope:** Represents the full taxonomy of PHP built-in entities.
- **Relationships:** One stub record subtype per tag value. The registry holds one typed map per subtype.

- **Name:** Dataflow Summary
- **Definition:** `flowsToReturn` on function and method entries records which parameter indices' data appears in the return value. This is an intrinsic property of the function's behavior, independent of any security analysis. Absence of `flowsToReturn` means the return value is a pure computation that does not contain parameter data.
- **Scope:** Applicable to function and method entities only.
- **Relationships:** Extracted from Psalm's `@psalm-flow` annotations. Consumed by dataflow analysis, taint propagation, type inference, and constant propagation in downstream modules.

- **Name:** Eager Immutable Loading
- **Definition:** All YAML files loaded at startup into immutable maps. No lazy loading, no caching layer. After loading, all queries are O(1) map lookup.
- **Scope:** Startup cost proportional to total entry count.
- **Relationships:** Maps are frozen read-only after construction. See [design.md](design.md) for the enforcement mechanism.

- **Name:** Data Extraction Pipeline
- **Definition:** Offline scripts extract signatures from JetBrains/phpstorm-stubs and dataflow annotations from vimeo/psalm stubs, then merge results into the YAML format. The extraction is a one-time process per PHP version upgrade. Output YAML files are committed to the repository and bundled in the JAR.
- **Scope:** Extraction scripts are development tools, not runtime dependencies.
- **Relationships:** phpstorm-stubs provides signatures (params, return types, class hierarchies, constant values). Psalm stubs provide `flowsToReturn` mappings.

## 3. Contracts & Flow

**Data Contracts**
- **With cobraphp-core:** Direct API. A function lookup by name returns the function's stub record with signature and dataflow fields (see [design.md](design.md) for signatures). Taint rules (source/sink/sanitizer) are owned and loaded separately by cobraphp-core.
- **With extraction scripts:** Scripts produce YAML files conforming to the tag-based format. Scripts are idempotent -- re-running produces identical output for the same input stubs version.

**Internal Processing Flow**
1. **Discover** -- Read `index.txt` manifest (auto-generated by Gradle `processResources`) to list all YAML files under `stubs/`.
2. **Parse** -- For each file, parse the YAML list. Dispatch each entry by `tag` field to the appropriate `StubRecord` subtype.
3. **Merge** -- Insert parsed records into per-type maps. Duplicate names within the same tag: last entry wins.
4. **Freeze** -- Wrap all maps as unmodifiable. No further mutation.

## 4. Scenarios

- **Typical:** Phase 1 encounters `strlen($x)`. A function lookup for `strlen` returns its stub record with the function's parameter types, return type, and an empty `flowsToReturn` set -- pure computation, no parameter data in the return value.

- **Boundary:** A new PHP extension adds `sodium_crypto_aead_encrypt`. A developer runs the extraction script against updated phpstorm-stubs, which generates a new `crypto/sodium.yaml` with the function's signature. `flowsToReturn` is absent (not in Psalm stubs), so the function's stub record defaults to no dataflow. A developer may later add `flowsToReturn` manually.

- **Interaction:** cobraphp-core loads the stubs registry for signature lookup, then loads its own taint YAML for security rules. `htmlspecialchars` has `flowsToReturn: [0]` in phpstubs (dataflow fact) and sanitizer classification in cobraphp-core's taint rules (security classification). The two concerns are independent.

See [design.md](design.md) for type specifications.
